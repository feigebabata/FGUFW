# Gameplay

- 管理业务逻辑 树形结构
- 兼容UI/存档 并自动化处理 引用部分依赖注入的思想 
- 测试数据可使用自定义ScriptableObject提供/或写死在模块内 (理想情况:把UI预制件拖进空场景 运行能测试基本交互)
- 使用UniTask处理异步功能 Part自动管理内部的UniTask

## 依赖注入
- 本身是控制反转的是实践用法
- Inject : 标记注入
- Dependency : 映射依赖关系
- Container : 处理被标记内容 创建时赋予对象依赖

## 树形结构
- 一个Play(GameObject)下挂载其他Part(GameObject)并递归
- 挂载方式A:在代码中手动执行 
  - 优点:方便在代码中查看引用 
  - 缺点:本身继承MonoBehaviour生命周期不好管理
- 挂载方式B:直接生成Play的预制件 然后手动添加Part的GameObject 
  - 优点:配置Part而不用编译
  - 缺点:用过加载预制件的方式来切换Part
  - 也许能方便单元测试
  - 但得控制初始化顺序

  ### 预制件挂载
  - 需要一个根据类型加载Part的工厂类
  - Part本身需要等待优先节点初始化完成 依赖Transform结构 自上而下广度优先
    - 只需找到自己的前一个 然后等待它初始化完成 自己是第一个就不用等待
  - 顺序: Part预制件实例化 > 等待前者初始化结束 > 初始化自己(进行依赖注入) > 直至整个Play完成初始化
  - 注入器一般挂在Play节点 测试场景随便放哪就行(但得保证场景中只能有一个)
